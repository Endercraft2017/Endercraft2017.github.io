# Penny inquiry forwarding

The existing contact handler can forward a validated inquiry to the private acquisition service before its existing SendFox notification. This is server-to-server only; frontend assets and public responses contain no signing credential, owner-only API access or financial assumptions. Existing validation, honeypot, source attribution, rate limiter and SendFox success/error behavior remain intact.

When Penny forwarding is enabled, the inherited optional Vercel AI Gateway triage is disabled for this acquisition path even if its legacy key remains configured. This avoids an untracked duplicate model call outside the shared server-side AI ledger. Disabling Penny forwarding preserves the prior optional triage behavior; no gateway or model is activated by this change.

Set `PENNY_WEBSITE_FORWARD_ENABLED=1` and a private `PENNY_WEBSITE_INTAKE_SECRET` of at least 32 characters on this website service. Set the same dedicated secret on the commercial-calculator service and enable its authenticated Penny intake. No new subscription or database is required. The destination is fixed at `https://calc.afkcube.com/webhooks/penny/website`; input cannot change its host/path or follow redirects.

Each actual validated request gets a new server event ID, actual receipt timestamp and one immutable body. Up to three bounded attempts reuse that event/body, with fresh purpose-bound HMAC request nonces. Acknowledgment must identify the expected website source, exactly one saved inquiry and no client quote capability. After acknowledgment, durable intake, qualification, revision history and private notices live on the calculator's existing persistent volume.

The website has no persistent volume and this implementation does not pretend to provide a durable caller outbox. A transient failed forward is retried within the current request. If all attempts fail, the normal SendFox owner email still sends and retains the full original inquiry as a recovery source. The request does not claim Penny accepted it. Owner-mail recovery is not yet an autonomous guaranteed replay mechanism. A form retry after an interrupted process is a new actual request, so cross-process exactly-once submission is not claimed.

The forward carries actual supplied contact, problem, current handling, selected needs, budget/timeline and attribution. Long problem/current-handling text is retained as bounded unresolved requirement chunks. It never accepts visitor-supplied feature IDs, salaries, internal rates, approval or sending instructions. Explicit quote language creates a quote-request hint; urgent/contract/refund questions route to owner attention. Ordinary inquiries request clarification; referral inquiries remain distinct from client pricing. AI App Review & Repair enters its fit stage, preserving separately paid diagnosis/repair/support boundaries. Only the owner reviews and sends every estimate.

Student inquiries with a real email can be captured; phone-only contact still uses the existing owner email path. No quote, agreement, payment, project, commission or paid service is created by this forward.

Referenceability: existing crawlable public service pages, readiness disclosures and the inquiry CTA are unchanged. This backend change connects an actual validated next step to the private inquiry workflow. Local tests verify signed request construction, bounded retries/stable IDs, actual-handler validation and preservation of owner email during an outage; they do not establish indexing, AI citations, actual production delivery or customer validation. Production proof requires an authorized controlled form submission, its actual saved Penny source and owner-alert receipt.
